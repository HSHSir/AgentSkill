# 从需求说明出图

截图有现成的像素可参照；需求说明没有，只能从**文字里把结构抽出来**。这份文档是那条路径的操作流程。

---

## 第 0 步 · 先判定输入类型

| 输入 | 特征 | 做法 |
|---|---|---|
| 界面截图 | 有图，看得见控件 | 走 `SKILL.md` 主流程：目测分区 → 套模式 → 填内容 |
| 需求文档 / 一句话需求 | 只有文字，或 TAPD 需求链接 | **走本文档** |
| 口头描述 | "做个强化界面，左边选装备右边看属性" | 走本文档，但先复述一遍结构再动手 |

需求说明画出来的图，**证据是需求文字，不是画面**。所以每画一个区域，都要能指回需求里的一句话。

---

## 第 1 步 · 抽五要素

把需求读一遍，填这张表。填不满的格子就是**要回头问的地方**，不要自己编。

| 要素 | 问什么 | 例（强化界面需求） |
|---|---|---|
| **页面目标** | 玩家在这页要完成的一件事 | 把一件装备强化到更高等级 |
| **数据对象** | 页面的主角是谁，有哪些字段 | 装备：名称、图标、品质、等级、属性、强化材料 |
| **操作** | 有哪几个按钮，主次是什么 | 强化（主）、一键强化（次）、返回 |
| **状态** | 需要体现哪些状态 | 材料不足、强化失败、等级上限、强化中 |
| **约束** | 数量上限、分页、权限 | 材料栏 4 格、等级上限 15 |

五要素里，**数据对象决定区域，操作决定底栏，状态决定子块样式**。

---

## 第 2 步 · 定界面类型（套模式）

拿第 1 步的结果，对照 `references/patterns.md` 的选择树。

判断依据只有三条：

1. 是不是覆盖在别的界面上 → 弹窗（模式 4）
2. 中间要不要留给 3D 场景 → 场景 + 浮层（模式 5）
3. 有没有"选中一个对象看详情"的关系 → 有则模式 3 / 1，没有则模式 2

选定模式后，**区域骨架照抄，只改宽度分配**。

例：强化界面 → 左（装备列表）+ 中（装备详情 + 强化槽）+ 右（材料/结果预览）→ 模式 2。

---

## 第 3 步 · 把需求翻译成区域

一条规则：**需求里的每一个"名词块"，对应一个区域或一个子块框**。

| 需求原文 | 落成 |
|---|---|
| "左侧显示装备列表" | 区域 B，内部用列表行 |
| "显示装备属性和强化后的属性" | 区域 C，内部用 `statList` 两列（当前 / 强化后） |
| "底部有强化按钮" | 区域 D 或 C 内底部，宽 160–200，居中于**父容器** |
| "材料消耗显示在右边" | 区域 E，内部 4 个 `slotRow` 格 |
| "成功率 / 消耗金币" | 贴在强化按钮上方一行，左标签右数值 |

**数量词直接落成格数**："4 个材料格"就是 `count: 4`，"3 个强化等级"就是 3 个方块。需求没写数量的，按经验取 3–5 并在线框图说明里注一句"数量待定，按 4 格示意"。

---

## 第 4 步 · 定内容层（每区域列清单）

写代码前，先在纸上（或回复草稿里）把每个区域的清单列出来，格式固定：

```
B 装备列表：标题「装备」+ 6 行（图标 40×40 + 名称 + 等级 + 品质色块），首行选中
C 装备详情：名称条 + 图标 120×120 + 品质/类型两行 + 属性 6 行（当前值 › 强化后值）+ 成功率一行
E 材料消耗：标题 + 4 格材料位 + 金币一行
```

清单写完再动手，能一次填满，不用"先画框再补内容"。

---

## 第 5 步 · 状态怎么表达（线框图的固定语法）

| 状态 | 画法 |
|---|---|
| 选中 | 该块用 `subfill` 浅色底，其余 `sub` 空心 |
| 未解锁 | 块内右下角画 r=8 的圆（锁位），或整块虚线 |
| 不足 / 不可用 | 块内底部一行小字「材料不足」「等级不足」 |
| 空位 | 虚线框（`dash`），或空心框 + 淡字「空」 |
| 进行中 | 块内一条横线表示进度条 + 百分比文字 |
| 数值变化 | `旧值 › 新值`，变化项后面加 `↑` |

这些是**线框图自己的语言**，不要画真实图标、不要画光效。

---

## 第 6 步 · 不要编

需求里没写的东西，一律不画：

- 没提过的按钮不画（哪怕"一般都会有返回键"）
- 没提过的数值不编（写「数值」而不是写 48）
- 没提过的页签不画
- 需求说"参考现有某界面"时，先去 `Docs/UI/` 找那页的区域骨架，套用其布局而不是重画

必须补的时候（比如需求漏了关闭入口），在交付回复里单列一行：「需求未提及，按惯例补了右上关闭」。

---

## 第 7 步 · 交付时多一句话

截图出图时，交付说"你看到的都要画"；需求出图时，交付要说明**推导链路**：

```
按需求「左侧装备列表 / 中间详情 / 右侧材料，底部强化」出四区。
需求未提及但按惯例补的：顶部返回、右上关闭。
数量按 4 格示意（需求只写"若干材料"）。
[链接]
```

这三行让用户能立刻判断"你理解的需求对不对"，比图本身更重要 —— 图画歪了还能改，需求理解歪了要重来。

---

## 完整示例：强化界面

**需求原文**（假设）：

> 新增装备强化界面。左侧显示可强化装备列表，点击后中间显示该装备当前属性和强化后属性，右侧显示强化所需材料和成功率。底部一个强化按钮。强化等级上限 15。

**第 1 步 五要素**

- 目标：把装备强化到更高等级
- 对象：装备（名称/图标/品质/等级/属性）、材料（种类/数量）、金币
- 操作：强化（主）
- 状态：材料不足、等级上限、成功率
- 约束：等级上限 15、材料 4 格

**第 2 步 定模式** → 有"选装备看详情"，无场景无弹窗 → 模式 2（顶栏 + 三栏）

**第 3 步 区域**

| 区域 | 落点 | 锚点 |
|---|---|---|
| A 顶部栏 | 标题「强化」+ 货币 + 关闭 | `left:'L', right:'R', top:'T', height:64` |
| B 装备列表 | 需求"左侧列表" | `left:'L', width:300, top:'A.bottom+8', bottom:'B-16'` |
| C 装备详情 | 需求"中间当前/强化后属性" | `left:'B.right+8', right:'E.left-8', ...` |
| D 材料与成功率 | 需求"右侧材料+成功率" | `left:'R-320', width:320, ...` |

底部强化按钮放 C 区内部底端，`cx:'center'`（父容器中心，不是画布中心）。

**第 4 步 内容清单**

```
B：标题「装备」+ 6 行（图标 44 + 名称 + Lv + 品质条），首行 subfill
C：名称条 + 图标 120 + 品质/类型 + 属性 6 行（当前 › 强化后）+ 成功率行 + 强化按钮 180×36
D：标题「所需材料」+ 4 格材料 + 金币行 + 成功率
```

**第 5 步 状态**：B 第二行起画锁位圆；C 属性变化项加 ↑；底部按钮 subfill。

**第 6 步 不编**：需求没提"一键强化"就不画；"等级上限 15"只写成文案，不画进度条。

**第 7 步 交付**：三行说明 + 链接。

---

## 需求出图的检查表

交付前逐条过：

- [ ] 每个区域都能指回需求里的一句话
- [ ] 需求里的数量词都落成了具体格数
- [ ] 主操作按钮在**父容器**居中，不在画布居中
- [ ] 补的控件在回复里单独列出
- [ ] 没编造需求里不存在的数值和按钮
- [ ] 区域数在 1–7 之间（超了就合并）
- [ ] 用 `slotRow` / `charStatPanel` / `pinCard` 等现成组件，没手算 pitch
